 Editor control channel shipped: the extension serves a loopback HTTP server (bearer token, URL and token handed over via spawn env) and the harness gains a `vscode_terminal` tool that runs commands in the user VS Code terminal with honest unavailable fallbacks. Two dsh 0.2.0-rc.2 contract facts cost real debugging: model-visible tools mount as agent preset children (`tools` exists only in preset fibers, never in the profile root), and `tools.register` rejects definitions without `output { schema, render }`. Verified live end to end on the harness rail: model called `vscode_terminal`, command executed editor-side, exit code reported back. Stopping the harness now also sweeps detached dsh processes by DSH_HOME (launcher tree kills left stale servers holding the port and the previous plugin build). Vendored plugin updates propagate: the staging stamp carries a plugin fingerprint, and the profile's pnpm copies of the adapter and core are diffed against the vendor trees on every prepare, deleted before reinstall, and re-verified afterward, because pnpm silently skips re-copying a `file:` dependency whose version did not change (observed in the wild: the profile kept the pre-terminal plugin, the preset child answered `never started`, session creation died, and the Preview Notice acknowledgement stopped persisting). A system-prompt section biases the agent toward the editor terminal whenever a control channel is present. Close/open hardening (0.0.4): the harness home is stable (`dsh-home`, no longer version-keyed; legacy `dsh-home-*` process trees are reaped once), the runtime install only counts as complete behind an `.install-complete` stamp so a window closed mid-npm reinstalls instead of crashing on a half tree, every spawn path reaps detached survivors of launchers the editor killed, a cross-window `start.lock` serializes prepare+spawn so restored windows adopt instead of double-spawning, adoption requires the running composition to match this build (a harness predating an update is drained and replaced), and closing a borrowing window releases the borrowed harness instead of killing it.

**Full-repo review pass (2026-10-05, 0.0.5):** every source file read end to end; findings fixed in one pass. The editor terminal read loop now registers its abort listener once per command instead of once per output chunk and clears its wait timer per iteration. The `vscode_terminal` contract drops `cwd`: the VS Code shell-execution API has no per-command working directory, so the tool tells the model to `cd` within the command, and requests from older plugins carrying `cwd` still parse. A ledger port is accepted only when it reports the handoff `apiVersion` this bridge speaks, so records can never reach a port with different accounting semantics. The harness exit handler clears the pid record only while it still names its own child, so a late exit event after a forced stop cannot blind the next window to a live replacement. A corrupt `snapshot.json` on disk is now replaced instead of failing prepare. Quarantine renames never overwrite older evidence. Only boot-time bridge settings trigger a draining restart: `ingestIntervalSeconds` re-arms the timer live, `drainTimeoutSeconds` needs nothing, and switching `autoStart` on starts a stopped harness. The `dshVersion` setting resolves at each use, so editing it takes effect on the next restart instead of after a window reload. Personality files configured on models (`systemMessageReplacementsFile`, absolute and present) now flow into the snapshot's `personalityFile`, which is the only path by which the adapter applies them (verified: the core's request pipeline never applies replacements itself). The no-vLLM-Copilot status bar item points at the extensions view, a command that exists. Verified with 66 vitest cases, the extension-host e2e handoff test, and a fresh VSIX install; live-harness drive of the personality path is the owner's next testrun.

**Non-blocking start (2026-10-05, 0.0.6):** every process the bridge runs during prepare (npm install of the dsh runtime, `plugin add`, profile creation, `--dump-config`, the detached-process sweep) was `spawnSync` on the extension host's event loop, so a cold boot froze the whole window, unrelated spinners included, for as long as npm took. All of it is awaited async now; only millisecond-scale system calls (`taskkill`, file stats) remain synchronous. Verified with `npm run bridge:check` (full rail against real dsh: prepare, boot, adoption, ingest, stop), 66 vitest cases, the extension-host e2e, and a fresh VSIX install.

**Editor tools over MCP (2026-10-05, 0.0.7):** the bespoke `vscode_terminal` plugin tool is retired. The loopback control channel now serves an MCP endpoint (`POST /mcp`), and the mount is dsh's own upstream `dsh-mcp-client` plugin, which the generated overlay adds as a preset child (`vllmc-editor-mcp`, streamable-http, bearer token as a header). The tool list therefore lives entirely on the extension side: adding tool number ten touches zero harness-side files, no vendor restage, no preset splice. v1 tools: `editor_state` (workspace folders, open tabs, active file with selection), `editor_diagnostics` (the problem panel, per file or window-wide), `editor_open_file`, `editor_open_diff` (provided content against the file on disk), `editor_notify`, `editor_ask` (question answered through a pick list or input box, dismissal reported honestly), and `run_terminal` (the old terminal tool folded into the same surface). The protocol handler is hand-rolled against the pinned MCP client 2.0 (read, not trusted: JSON responses accepted, 405 on the SSE probe tolerated, 404 on DELETE tolerated, notifications expect 202, and the client aborts unless `initialize` echoes a protocol version it offered, so the handler echoes). Zero npm dependencies, per the zero-dependency law. Tool calls publish a drain marker while executing, so a restart still waits for an in-flight editor build. The overlay emits the mount only when a control endpoint exists, so headless prepares compose a harness without editor tools instead of one dialing a dead port. `npm run bridge:check` now proves the real composition, not just the overlay text: real dsh resolves the generated preset child from the profile graph and dials the endpoint carrying the bearer header (`initialize x1, tools/list x1, unauthorized 0`). Same-day owner rulings recorded: MCP v1 tool set approved as built; the upstream `dsh-git-rollback` npm plugin gets mounted as an overlay row in a later release, on by default, MIT attribution to `THIRD-PARTY-NOTICES.txt`; `extensionKind: workspace` stays, remote and WSL windows run the bridge beside dsh on the host (loopback and token never cross the wire), with `asExternalUri` for the harness URL and a WSL smoke run of the `pkill` sweep as the open items of that future unit.

**Drive-letter session fix and notice seed (2026-10-05, 0.0.8):** a window opened via a lowercase drive path (`g:\...`) made the workspace handoff register the folder with that exact spelling while dsh resolves session cwds to `G:\...`; the exact-string upsert missed the existing row, and every session died at create with `session/workspace-attach-failed: its cwd resolves to 'G:\...'` (found live by driving the harness UI with a browser automation and reading the rejected RPC). `registerDefaultWorkspace` now writes the canonical form, matches rows case-insensitively on Windows, and heals a previously written lowercase row in place, id and session history intact. Separately, the Preview Notice acknowledgement can never persist in a no-account profile: the client renders the notice until `ui-settings-general.welcomeNoticeVersion` equals its constant exactly, and the persistence path reports "could not be saved" forever without an account (this was already failing in the 0.0.2-era logs, previously misattributed to a stale plugin). By owner ruling the overlay now states the acknowledgement itself (`welcomeNoticeVersion: 2026-09-28.1`, bumped with each dsh pin update, upstream constant certified in `dsh-client-ui-settings-models`). The underlying no-account ack path remains an upstream bug worth reporting once.

**Embedded harness view and picker prune (2026-10-05, 0.0.9):** the harness opens inside VS Code by default. VS Code 1.140 removed the Simple Browser extension outright (its `simpleBrowser.show` is gone from the command registry, certified on the extension-host rail), so the opener probes the replacement built-in `workbench.action.browser.open` first, then `simpleBrowser.show` for older builds and VSCodium, then falls back to the system browser with a visible notice. The `dsh-bridge.openIn` setting (default `embedded`) controls it. The URL with its UI token crosses only as the command argument, never a log. The harness server itself never opens a browser: the spawn passes `--no-open` (upstream `dsh-web-app` defaults `openBrowser` to true and hands the URL to the OS otherwise). Before spawning, the workspace handoff also prunes sessionless case-duplicate rows of the registered folder: dsh lists every row in its picker, and the pre-fix lowercase twins showed as a second identical workspace whose sessions all die. Rows owning sessions are never touched. Owner ruling this evening: an embedded chat surface styled after Copilot (participant UI fed by `dsh-acp`, recon first) is a future unit.

**Chromeless panel attempt and retirement (2026-10-05, 0.0.10 shipped, 0.0.11 retired):** the owner's complaint about the browser tab was exactly one address bar, and research says the built-in Browser area cannot hide it: every `browser.*` configuration key in the 1.140 workbench bundle was scraped, none hides the toolbar (`workbench.browser.showInTitleBar` only relocates it), and the deleted Simple Browser had an address bar too. A webview panel whose entire pane was an iframe of the harness URL shipped in 0.0.10 and died the same evening: the harness mints its browser session as an `HttpOnly; SameSite=Strict` cookie after the token redirect, and Chromium neither stores nor sends Strict cookies in a cross-site frame (an extension webview's document origin is never the harness origin). The iframe therefore only ever rendered the server's 401 body. The Browser area keeps working because it loads the page top-level, where the cookie applies. The panel mode is deleted in 0.0.11; do not re-propose iframe embedding unless upstream ships `Partitioned` cookies (see docs/upstream-issues.md; a loopback proxy that rewrites cookie attributes was considered and rejected as a permanent data-plane liability).

**Served-model catalog and harness-safe model ids (2026-10-06, 0.0.12):** dsh's picker offered a model its server had stopped serving (retired from the vLLM endpoint, still in the registry), and selecting it produced only an error toast, while Copilot's own picker had already hidden it. Two fixes. First, prepare now probes each configured server with the core's own `detectServerType` + `listServerModels` (the literal code the picker runs, imported from the profile-installed core where pnpm resolved its dependencies; the raw vendor staging has no `node_modules` and cannot be imported) and drops models a nonempty served list demonstrably lacks; an unreachable server or empty list keeps everything, so a network hiccup can never empty the harness catalog. Second, snapshot model ids are re-keyed to the user-chosen `displayName` (uniquified on collision, falling back to the wire id), because dsh prints the model id in its UI and registry ids embed hostnames: the harness chip went from `vllmc/<wire> on <host>` to `vllmc/<display name>`, which also scrubs private server names from any third-party UI. Default, aux choices, personality attachment, and warnings all cross the re-key map; wire ids in requests are untouched. Old sessions re-pick their model once, the same one-time cost as any model removal. Companion document `docs/vllm-copilot-integration.md` lists what the main extension should change to delete this duplicated policy (one shared served-model resolver, a typed core surface, display-name uniqueness, an ingest helper), with the workarounds this repo carries until each lands.

**Served-catalog hotfix (2026-10-06, 0.0.13):** 0.0.12 compared wire ids against `listServerModels` entries as if they were strings; the core answers records (`{id, max_model_len, ...}`), so every model looked unserved and `prepare` refused to boot a healthy setup with "nothing honest to offer". Entries are normalized to wire ids before comparison, a tripwire feeds object-shaped listings so the wipe cannot return, and the probe now runs against live servers before shipping. Duck-typing an untyped core surface without reading its return statements: recorded as exactly the drift `docs/vllm-copilot-integration.md` P2 exists to kill.

**Two-window and rail-honesty pass (2026-10-06, 0.0.14):** full-repo review findings fixed in one batch. Auto-restart on a registry or bridge-settings edit is now the spawning window's job alone: every window hears the same configuration event, and a borrowing window restarting meant tree-killing a harness it does not own while two windows' stop-and-sweep could cut down a freshly respawned one (symptom: a spurious "exited on its own" toast after editing the model list with two windows open). The served-catalog loader moved out of `extension.ts` into `src/bridge/core-catalog.ts` and the `bridge:check` and live rails now build the same source the editor does, so `resolveServedModels` and `buildDisplayKeys` are finally exercised by the ship gate instead of only by unit fakes; the rail registers a model its wiretap does not serve and fails unless the real core's `absent` verdict prunes it from the snapshot with a readable warning. The loader invalidates its cached module when staging restages the core, which fixes the dev-loop case of swapping vLLM-Copilot inside one window and getting the previous build's verdicts. The palette context keys became true: `commandPalette` when-clauses now hide Start while running and hide everything when vLLM-Copilot is absent. The MCP instructions told the model to use a tool named `ask_user` that does not exist (it is `editor_ask`), the Node floor told in errors and README was 20 while the harness packages require 22, and an unreadable `config/dsh.json` pin silently fell back to `latest`, booting an uncertified dsh against certified overlays; it now refuses. `stage-core.mjs` with no flag stages the sibling `../vLLM-Copilot-public` working tree when present, the same default the rails' `VLLMC_EXT_DIR` uses, so gate and stage cannot disagree about which core is under test. 78 vitest cases.

**Marketplace identity and dogfood pass (2026-10-06, 0.0.15):** the manifest now mirrors the main extension: publisher `System-Sciences`, author block, sponsor, changelog, categories, keywords, and an `extensionDependencies` entry on `System-Sciences.vllm-copilot`, so the two ship as one family. ## Build-time rulings (owner, 2026-10-05)

- Core distribution: the bridge copies the compiled core (`out/core`) from the installed vLLM-Copilot extension into `$DSH_HOME/vendor/vllm-copilot-core/` with a version stamp, and stages the adapter plugin as a sibling directory whose `package.json` depends on `vllm-copilot-core` via the relative `file:../vllm-copilot-core`. The profile installs only the plugin; pnpm links the core beneath it. No npm publish, no git-tag dependency, nothing compiled on the user's machine. The earlier "npm git dependency on a tag" assumption is retired: tags carry source only (`out/` is gitignored, no prepare script), so it could never have installed a runnable core. Upstream `docs/dsh-bridge-plan.md` still carries the retired wording and needs a sync edit at the next touch of that repo. On extension update the bridge re-stages, drains active requests, and restarts dsh.
- Companion expected, polite fallback: with the vLLM-Copilot extension absent, dsh still launches and the user configures providers the classic way; the bridge shows a persistent install reminder and its own features (snapshot, ledger, health) stay dark. The bridge is not a standalone product.
- One ledger: the adapter writes completed-request records to `$DSH_HOME/vllmc/usage-outbox/`; the bridge ingests them into the main extension's canonical usage owner, so dashboard totals, cost, last-request, and resets include harness traffic with no double count. A dashboard-invisible ledger under DSH_HOME remains forbidden.

## Steps

### Step 1: Plugin loads from a real npm install

The 2026-10-03 spike loaded the plugin via a `file:///` absolute URL because bare specifiers did not resolve from dsh's module loader inside the npx cache. Proper package installation was assumed for production but never proven, so prove it first: `plugin/` becomes a package with `export const inject = ['llm']`, registers an `LlmAdapter` for provider `vllmc`, `stream()` yields canned `block-start`/`text-delta`/`block-end`/`usage`/`finish` chunks. Install it into a dsh plugins location and boot `npx @deepseek-ai/dsh@0.2.0-rc.2 web --patch <overlay> --no-open` with privacy rows disabled.

Done when: a dsh session renders the canned text with the plugin resolved through normal package resolution (no `file:///` in the patch), and the overlay comes from a generator script checked against `--dump-config` output, not a hand-written yml.

Certified 2026-10-05 against dsh `0.2.0-rc.2`. Load path: the plugin declares `dsh.bundle.patch` in `package.json`, `dsh plugin --profile <name> add file:<dir>` installs it as a profile pnpm dependency and selects the bundle, and the bundle patch inserts the row by bare specifier (the launcher's runtime resolution serves `@deepseek-ai/*` imports from the installation; declare the dsh-llm peer to get composition-time version policing). `scripts/step1-boot-check.mjs` re-proves all of this per version bump; `scripts/generate-overlay.mjs` refuses to emit rows absent from the dump (headless lacks `desktop-product-telemetry`; the web composition has it).

### Step 2: Adapter against the real core (gate 2)

Wire the staged core (dev loop: `node scripts/stage-core.mjs` clones the pinned tag into `temp/`, compiles, and stages `temp/stage/vllm-copilot-core/` exactly as production staging will), then replace canned output with the real request path. Fixtures, each naming its breakage:

- Frozen `GenerateOptions`: adapter builds detached wire messages, never mutates harness input.
- Leading-system-message and one-shot `system` inputs both project correctly.
- Tool calls/results/error-results round-trip (`toolCallId`, arguments diffed, name arrives exactly once).
- Reasoning: streamed reasoning replays on the next turn's assistant message in the backend-correct field (the pi-ai round-trip fact is not proof for the adapter path; prove it here).
- Usage: cache-inclusive core counts vs dsh's `inputTokens` converted explicitly, totals preserved.
- `purpose: 'session-title'` and `'compaction'` calls metered and aimed per config, not silently free.
- `signal` cancellation settles the core request.
- Errors map into dsh's `LlmError` taxonomy, no OpenAI envelopes.

Done when: fixtures green in vitest against a local wiretap mock (rebuild: OpenAI-compatible endpoint logging request bodies per session), plus one manual `npx` run where the mock asserts the outbound body carries our sampling params and headers while dsh's `compat` stays unset.

### Step 3: Supervisor, snapshot, overlays (gate 3)

VS Code extension skeleton: detect Node and dsh, install offer, spawn with dedicated `DSH_HOME`, `dsh.pid` write plus stale-pid reap at activation (dispose does not fire on hard host crashes), settings snapshot rewrite with explicit active-request drain before restart, health status bar, "Open harness" command. Snapshot is versioned; plugin rejects unknown versions loudly.

Done when: kill the dsh process externally, reopen the window, one clean supervised instance remains; change a registry entry, snapshot file updates, restart honors the drain policy; completed-request records reach the main extension's usage owner idempotently (no double count, resets respected, dashboard totals include harness traffic).

### Step 4: Real backend turn (gate 4)

One agent turn with a tool call through the packaged core against a real server the owner configures locally (credentials enter only via the owner's own vLLM-Copilot settings, never this repo or its logs). Then a reasoning-preserving follow-up. dsh-side badges and our ledger both agree with backend totals including title and compaction calls.

### Step 5: No-Copilot editor (gate 5)

Fresh VSCodium install from Open VSX: main + companion activate clean, registry and dashboard work, one complete dsh agent turn with no Copilot present. Publication duty: every release of both extensions publishes to Open VSX too.

## Rails

- dsh semver is decorative: certify against a pinned version, regenerate overlays only through `--dump-config`-checked templates, fail loudly on unknown rows. Re-run the Step 1 boot check on every dsh version bump before adopting it.
- Display law: fixtures, logs, and this repo print wire model ids and user-chosen display names only; ids built from config carry hostnames.
